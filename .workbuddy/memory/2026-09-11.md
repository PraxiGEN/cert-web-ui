- **四向样式**：

## 根证书重新生成：调研结论（方案未定，待用户拍板）

读懂现状后可用于设计的关键事实：
- `ca.RootCA{ Cert, Key *ecdsa.PrivateKey }` —— **根密钥类型硬编码 EC P-256**（`loadRootPair` 会拒绝非 EC 根）。要支持 RSA/P-384 根需把 `Key` 泛化为 `crypto.Signer`。
- `InitRoot` 有全局 `rootCache`（`rootMu` 保护）：轮换必须替换缓存，不能只改文件。
- `ca.Renew(cfg, folder)` **已经就是「用现有私钥 + 当前根重签」**，并会刷新 serial/IssuedAt、清除 Revoked 标记、沿用 metadata 里的原有效期。→ **「轮换根 + 全量重签」只需 `RotateRoot()` + 对全部 `origin=issued` 目录循环 `Renew()`**，几乎零新代码。
- CRL 由当前根签名（`writeCRL` 用 `root.Cert/root.Key`）。轮换后旧根签的 `crl.pem` 会失去验证能力 → 必须归档旧 CRL，并归档/重置 `revoked.json`。
- 导入证书（`origin=imported`）**无法重签**，任何轮换方案下都只能保持原样或删除。

## 实施：根证书轮换（Rotate Root）

用户拍板：**轮换 + 全量重签**（选择1），并要求「多个提示和条件、增加门槛」；算法**可选**；有效期沿用配置值 10 年。

### 后端
- **`ca/pki.go` 泛化根密钥**：`RootCA.Key` 由 `*ecdsa.PrivateKey` → `crypto.Signer`；新增 `generateRootKey(keyType)`（ec-p256/p384/p521、rsa-2048/4096，未知回退 P-256）；`generateRoot(cfg, keyType, caName)` 签名字段改为 `key.Public()`；`loadRootPair` 去掉 EC 断言，改为 `publicKeysEqual()`（PKIX 编码后 `bytes.Equal`）**校验私钥与证书配对**，错配直接启动报错。
- **`config`** 新增 `RootKeyType`（env `CA_ROOT_KEY_TYPE`，默认 `ec-p256`）。
- **新增 `ca/rotate.go`**：`RotateRoot(cfg, opts) (RotateResult, error)`。顺序刻意「**先生成 → 再归档 → 最后落盘**」，写新根失败会 `rollbackMoves()` 把归档的旧根搬回来，杜绝「旧根已删、新根没写上」的信任锚真空。
  - `confirm` 必须逐字等于当前根 CN，否则 400。
  - 归档 `CA_HOME/archive/root-<20060102-150405>/`：`root_ca.crt`(0644) + `root_ca.key`(0600) + `crl.pem`。
  - **`revoked.json` 故意不归档**：吊销记录按序列号存，与新根不冲突；保留它导入证书的吊销状态才不会丢。归档旧 CRL 后**用新根重建 CRL**（旧 CRL 由旧根签名，留着客户端验签必失败）。
  - 重签直接复用 `ca.Renew()`（本身就是「原私钥 + 当前根重签」），`origin=imported` 计入 `untouched` 跳过。
- **`api`**：`writeJSONStatus()`；`POST /api/backend/root/rotate`（`withAuth` 包裹 + 服务端 `confirm` 硬校验）。
- `ca.RootInfo` 新增 `common_name`（前端确认词直接用，不用解析 RFC2253）。
- 全项目跑了一次 `gofmt -w` 统一格式。

### 前端（三道门槛）
1. 「根证书」卡底部 `.danger-zone` 红色危险区 + 「重新生成根证书…」按钮。
2. `#rotateOverlay` 模态：红色警告框（4 条后果）、实时影响面数字（重签 N 张 / 导入 M 张）、新根 CN 与算法、是否立即重签；**二次确认输入框必须逐字等于当前根 CN 才解锁提交按钮**（trim 后比对）。
3. 提交前浏览器原生 `confirm()` 再念一遍影响面；`ROTATING` 标志位在生成期间（RSA 可能数秒）禁止关闭面板。
- 结果页 `showRotateResult()`：新根名称/算法/到期/指纹、重签成功数、导入跳过数、**旧根归档路径**、失败明细、「下一步必做：分发新根」+ 下载新根按钮。

### 前端：三个通用组件（取代 9 处 `alert` + 4 处 `confirm`，现为 0 残留）

## release 工作流升级：版本变更自动发布 + 手动触发；端口 8080 → 16850

### workflow（单文件三触发）
- **push main**：解析 `config/config.go` 的 `getenv("APP_VERSION", ...)` 默认值 → tag 不存在则自动打 tag 并发布。**发版 = 改一行版本号 + push main**。
- **workflow_dispatch**：手动跑，`inputs.version` 可留空（= config.go 值）或填 `v1.2.3`/`1.2.3`（自动补 v 前缀）。
- **push tag v\***：直接发布该 tag。
- **关键坑：内置 `GITHUB_TOKEN` 打的 tag 不会触发新 workflow run**（防递归）→ 「打 tag」与「构建发布」必须同一 workflow：`resolve` job（打 tag，输出 version）→ `docker` job `needs: resolve`，其 `if` 需兼容 resolve 被 skip（tag 触发时 resolve 直接跳过，docker 用 `github.ref_name`）。版本已存在 → resolve 输出空 version → docker 跳过（不重复发布）。
